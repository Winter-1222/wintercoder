# 开发、教学与复盘约定

## 1. 注释语言

源码注释与 docstring 使用中文，说明“是什么、谁调用、输入输出、为什么”和边界条件，不逐行翻译代码。类名、函数名、协议字段和第三方 API 名称保持英文，避免自造翻译导致检索困难。

好的注释：

```python
# 标准输出属于 NDJSON 协议通道，普通日志必须写入标准错误。
```

不需要的注释：

```python
# 把计数器加一。
counter += 1
```

### 1.1 零基础源码注释标准

源代码本身也是本项目的教材。每个新建或修改的源码文件都要按下面的层次补充说明：

1. **文件顶部**：说明这个文件属于哪一层、解决什么问题、上游是谁、下游是谁。
2. **类型与字段**：解释它代表的现实概念。不能只写“字符串”，还要说明这个字符串在链路中用来做什么。
3. **类、函数和方法**：说明调用者、参数、返回值、副作用，以及单独抽出它的原因。
4. **关键分支**：`switch case`、状态机状态、异常降级、权限判断和并发分批必须逐个解释触发条件与状态变化。
5. **框架概念**：第一次使用 `reducer`、React Effect、IPC、异步生成器等概念时，要在离代码最近的位置用当前项目举例解释。
6. **不明显的语法**：展开运算符、不可变更新、可选链等会影响理解的写法，需要解释结果长什么样。

例如 `chatReducer(state, action)` 就是 React 语境中的 reducer：它接收“旧状态”和“发生了什么”，返回“新状态”。它不负责调用 API，也不直接修改界面。每个 `case` 都是在回答一种 action 到来时哪些字段应该变化。

注释不是越多越好，而是要让初学者能沿着注释回答四个问题：当前数据从哪里来、长什么样、接下来去哪里、为什么不在别处处理。

### 1.2 不能直接写注释的文件

JSON 配置、图片等格式本身不允许或不适合写注释，职责统一记录在 `docs/PROJECT_STRUCTURE.md`。`scripts/test-all.ps1` 为兼容 Windows PowerShell 5 保持纯 ASCII，中文逐行说明放在第 0 章 README；这是编码兼容例外，不代表业务源码可以省略中文注释。

## 2. 每章文档布局

```text
docs/chapters/01-llm-ui/
├─ README.md          # 教学：概念、设计、代码导航和练习
├─ DEVLOG.md          # 开发过程、决策、问题与提交
└─ MANUAL_TEST.md     # 手动步骤、预期、实际与坑
```

进入新章时才创建该章目录，避免提前生成大量空文档。

## 3. 零基础教学标准

用户默认是几乎零基础的初学者。章节 README 必须做到：

1. 先写“这一章跑通后能看到什么”，再讲抽象设计。
2. 给出三轮推荐阅读顺序：先概念、再按数据流读源码、最后带协议字段全局搜索。
3. 第一次出现进程、IPC、stdin、异步迭代、reducer、Schema 等术语时，用日常语言和当前项目例子解释。
4. 至少选择一个具体操作，逐步追踪到最终结果。每一步写明文件、函数、输入、输出和为什么存在。
5. 给出数据在不同层的具体形状，例如 JavaScript 对象、NDJSON、Python Envelope、React action。
6. 明确区分真实实现、Fake/测试实现和未来设计，不能让读者误以为计划已经可用。
7. 提供按现象排错表、从简单到困难的可跟做练习，以及带答案的自测题；扩写章节时保留并同步更新这一部分。
8. 新能力加入后同步扩展链路，不能只在“小步实现”中增加一个文件名。

教程首先帮助读者建立心智模型，不要求读者第一次阅读就掌握所有语言语法。模板见 `docs/templates/MODULE_GUIDE_TEMPLATE.md`。

## 4. 开发循环

每个小步遵循：

1. 在教学文档写一句本步要解决的问题。
2. 先写领域类型或失败测试。
3. 实现最小代码。
4. 运行相关自动化测试。
5. 按手测文档操作一次并记录实际结果。
6. 在 DEVLOG 写遇到的错误与取舍。
7. 检查 diff 后提交 Git。

当前协作方式不在功能完成后自动执行第 7 步。应先报告改动、启动命令与测试方法，等待用户明确要求后再提交。

DEVLOG 中的提交号采用下一次文档提交回填：功能提交先记录待回填标记，随后在同章的 `docs` 提交中填入功能提交号；不修改已经创建的提交来制造自指记录。

## 5. 环境前置

- 已安装 Conda，存在 `mycoder` 环境；当前基线为 Python 3.12.13。
- 已安装 Node.js 与 npm；当前基线为 Node.js 24.15.0、npm 11.12.1。
- Day 1 会在 `pyproject.toml` 与 Electron lockfile 中锁定实际依赖版本，并把安装、启动、测试命令写入 README；总体路线不提前虚构尚未生成的命令。
- 真实集成测试需要 DeepSeek API Key、可访问官方端点的网络；第六章高德手测另需高德 MCP Key。
- 没有真实 Key 时仍可使用 FakeLLM、FakeTransport 完成默认自动化测试。

## 6. 测试分层

- 单元测试：消息转换、JSON 碎片、权限规则、批次分区等纯逻辑。
- 组件测试：使用 FakeLLM、FakeTool、FakeTransport，不访问网络。
- 集成测试：Python Bridge 与 Electron IPC、会话落盘等进程或文件边界。
- 手动测试：真实 DeepSeek、真实窗口、真实 MCP 和用户确认交互。

真实 API 不放进默认自动化测试，以免测试不稳定和产生费用。

测试实现放在本地 `tests/` 或 `*.test.*` 文件中，由 `.gitignore` 排除。Git 只记录测试策略、命令和结果；因此新克隆不会自动包含这些本地测试夹具。

## 7. 密钥与日志

- 示例配置只写 `${DEEPSEEK_API_KEY}`、`${AMAP_MCP_KEY}`。
- API Key 不能出现在异常字符串、请求 dump、截图或开发日志中。
- 默认日志记录请求 ID、模型、耗时、Token、事件类型，不记录完整对话正文。
- 需要调试正文时使用临时显式开关，结束后删除产生的日志。

## 8. Git 约定

提交格式：`类型(范围): 中文说明`。

常用类型：

- `feat`：新增功能。
- `fix`：修复问题。
- `test`：补充测试。
- `docs`：文档与复盘。
- `refactor`：不改变行为的重构。
- `chore`：工程配置。

提交前至少检查：相关测试通过、无密钥、无运行数据、文档同步、注释为中文。
