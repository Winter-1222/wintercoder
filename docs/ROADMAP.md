# 霁雪一周开发路线

## 当前进度（2026-08-30）

- 第 0 步工程基线：已完成并通过真实 Electron 进程回归。
- 第一章 A 步 FakeLLM 流式界面：已完成。
- 当前下一步：配置加载与 Anthropic SDK 适配器，然后实现 ConversationManager。
- 尚未进入：真实 DeepSeek、多轮历史、工具系统及后续章节。

## 1. 一周交付目标

七天后的 `v0.1.0` 应该能完成一条完整链路：

> 用户在 Electron 输入任务 → DeepSeek 流式回复 → 模型选择工具 → 权限系统判断或请求确认 → Agent 多轮执行 → UI 展示事件 → 对话和必要记忆落盘 → 可连接一个 MCP Server。

“一周完成”按教学型 MVP 计算，不把“生产级接口形状”误解为“一周内达到生产部署安全等级”。本周保留正确边界和测试点，但主动砍掉安装包、多供应商实现、强系统沙箱、复杂检索记忆和多层子 Agent。

## 2. 每章共同的完成标准

每一章只有同时满足以下条件才算完成：

- 功能代码可以运行，源码注释使用中文。
- 核心纯逻辑有自动化测试；外部 API 用假流或录制事件测试，不靠反复烧 Token。
- `docs/chapters/XX-name/README.md` 讲清概念、边界和关键代码。
- `DEVLOG.md` 记录目标、改动、取舍、错误、修复和提交号。
- `MANUAL_TEST.md` 写清准备、操作、预期结果、实际结果和常见坑。
- 不提交密钥或运行时对话数据。
- `git status` 清晰，按小步形成可回退提交。

## 3. 七天节奏

| 天数 | 主要内容 | 当天必须可演示的结果 |
| --- | --- | --- |
| Day 1 | 第 1 章：LLM、对话、Electron UI | UI 中看到 DeepSeek 流式回复和状态栏 |
| Day 2 | 第 2 章：工具系统 | 模型可调用只读工具，UI 显示调用与结果 |
| Day 3 | 第 3 章：Agent Loop | 能连续执行多轮工具调用，可取消，可切 Plan/Do |
| Day 4 | 第 4、5 章：Prompt 与权限 | Prompt 可组合；危险命令拒绝；写操作弹确认 |
| Day 5 | 第 6 章：MCP | 后台连接 MCP，高德工具可延迟发现并调用 |
| Day 6 | 第 7、8 章：上下文与记忆 | 大结果落盘、可手动压缩、会话可恢复、记忆可索引 |
| Day 7 | 第 9 章最小版、回归与文档 | 一个只读子任务可运行；全链路手测通过并打标签 |

第 0 步占用 Day 1 的前半天，第一章占用 Day 1 后半天并可延续到 Day 2 上午；表格表示主要关注点，不表示每章必须在自然日零点切换。

Day 6 和 Day 7 风险最高。发布门槛分成两个明确层级：

- `v0.1.0-core` 必须完成第 1—6 章、第 7 章大结果落盘与手动压缩、第 8 章会话持久化，以及完整权限回归。
- `v0.1.0` 在 core 基础上再完成自动压缩、自动记忆和第 9 章最小子 Agent。

若一周结束时只达到 core，就创建 `v0.1.0-core` 标签并继续开发，不能把未完成能力写成 `v0.1.0`，也不能以赶进度为由削弱权限防线。

## 4. 第 0 步：工程基线

### 小步

1. 初始化 Git 主分支和忽略规则。
2. 创建 Python `src` 布局、`pyproject.toml`、pytest、类型检查和格式检查。
3. 创建 Electron + React + TypeScript 项目，先显示空壳窗口。
4. 实现最小 Python 子进程 Bridge，只处理 `bridge.hello`、`bridge.ready` 和协议级 `error`，暂不处理聊天。
5. 写 `.env.example`，真实 Key 只从环境变量读取。
6. 建立章节文档目录和三类模板。
7. 添加一条同时运行 Python 测试与前端测试的开发命令。

### 验收与手测

- `conda run --no-capture-output -n mycoder python -V` 使用 Python 3.12.13。
- Electron 窗口能打开、收到 `bridge.ready` 并关闭，关闭后没有残留 Python 子进程。
- `git status` 不出现 `.env`、会话或运行缓存。

### 常见坑

- Windows 下 Electron 启动 Conda 命令时的路径和引号。
- Python stdout 被日志污染，导致 NDJSON 无法解析；日志必须走 stderr。
- 一开始就铺满全部目录，留下大量永远不用的抽象。

## 5. 第一章：让 AI 开口说话并可视化

### 目标

完成最小的多轮流式对话闭环，同时锁定 LLM SDK 隔离边界。

### 小步

1. 定义 `LLMConfig`、内部 `Message`、API `Message`、`Usage` 和第一章事件 `stream_text`、`usage`、`turn_complete`、`error`；工程初始化复用第 0 步成果，不重复搭脚手架。
2. 定义 `LLMClient` 协议及工厂；首版只注册 `anthropic`。
3. 用 `AsyncAnthropic` 实现 DeepSeek Anthropic 端点适配器，转换 SDK 异常。
4. 解析文本、Token 和停止原因事件；为事件顺序写假流测试。
5. 实现 `ConversationManager` 与 `to_api_format()` 的过滤、合并、交替校验。
6. 扩展第 0 步的 NDJSON Bridge，加入 `chat.send` 与第一章业务事件，并由 Electron Main 转发。
7. 实现标题栏、对话区、状态栏、输入区四块 UI。
8. 流式时显示纯文本；收到完成事件后再 Markdown 渲染和清洗。
9. 接入三个模型选项，默认 Flash；视觉模型暂时只处理文本。

配置加载规则在本章固定下来：默认读取 `config/models.yaml`，本地可用 `config/models.local.yaml` 覆盖同名模型；`${VAR}` 只由 Python Bridge 从进程环境展开；本地覆盖优先于默认配置，环境变量只负责替换值而不新增结构。启动时一次性校验四字段、协议和模型目录；缺失 Key 时允许 UI 启动，但发送消息前返回可操作的配置错误。任何日志都只显示 Key 是否存在，不显示值。

### 自动化测试重点

- SDK 类型不会出现在领域接口返回值中。
- 相邻同角色消息可合并，非法开头或空消息可诊断。
- 中文、多字节字符、断行和 Markdown 围栏被切成任意片段时仍能正确重建。
- API 中断后内部消息标记为失败，不把半截回复当成已完成历史。

### 手动测试

1. 连续问“我叫小霁”和“我叫什么”，验证完整历史随请求发送。
2. 要求输出含标题、列表、代码块的 Markdown，观察流中纯文本和完成后渲染。
3. 在长回复中断网，确认 UI 给出可理解的错误且仍能再次发送。
4. 切换 Flash/Pro，确认状态栏模型名与实际请求一致。
5. 切换 Vision Exp，确认 UI 明确标注“实验、首版仅文本”，文本请求可用且没有图片上传入口。
6. 检查 Token 和计时：流式中实时更新，结束后不再跳动。

### 常见坑

- DeepSeek 的 Anthropic `base_url` 需要使用 `/anthropic` 端点。
- SDK 流事件并非都含文本，不能假设每个 delta 都可直接拼接。
- 每个文本碎片都渲染 Markdown 会闪烁，并可能产生未闭合代码块。
- Renderer 直接持有 API Key 会形成泄露面。

### 退出条件

不调用工具时，连续完成 10 轮对话无事件乱序、重复文本或进程泄漏。

## 6. 第二章：工具系统

### 目标

让工具定义、执行、错误反馈和 UI 展示形成闭环，上层不依赖 Anthropic 工具类型。

### 小步

1. 定义 `Tool` 接口、`ToolContext`、`ToolResult` 和 `ToolCall`。
2. 实现 `BaseTool` 工厂式通用实现，默认 `isConcurrencySafe = false`。
3. 用 JSON Schema 校验输入；校验失败转换成 `isError: true` 的结果。
4. 实现注册、重复名拒绝、启停、条件启用和分类查询。
5. 实现 Registry 的 `to_api_format()`，只输出启用且非延迟的工具。
6. 扩展消息内容块：`text`、`tool_use`、`tool_result`；扩展业务事件联合类型，加入 `tool_use` 与 `tool_result`。
7. 实现 tool JSON 碎片累积器；按内容块索引分别缓存，停止时解析。
8. JSON 解析失败时发出错误事件并保留原始预览，不终止整个流。
9. 先实现 `ReadFile`、`Glob` 两个只读工具；写入和 Shell 等第五章权限完成后再默认启用。
10. UI 添加工具调用卡片，展示名称、输入摘要、结果状态和耗时。

### 自动化测试重点

- 工具名重复、禁用、Schema 非法和输入校验失败。
- 同一个响应交错出现文本块和多个 tool_use 块。
- JSON 在任意字符边界拆分、空 input、畸形 JSON 和未知 delta。
- `metadata` 进入 UI 事件但不进入发给模型的 `tool_result.content`。

### 手动测试

1. 让模型读取一个存在的文件，确认调用卡片和内容正确。
2. 读取不存在的文件，确认模型收到错误结果后能改用 Glob 查找。
3. 禁用 ReadFile 后要求模型读取，确认 Registry 不再向 API 暴露它。
4. 用测试夹具模拟损坏的 JSON 流，确认对话仍可继续。

### 常见坑

- tool input 是 JSON 碎片，不是每个 delta 一个完整对象。
- 多个内容块依靠 index 区分，单一全局缓冲区会串数据。
- 把可恢复的工具失败抛成系统异常会无谓中断 Agent。

### 退出条件

模型能完成“先 Glob 找文件，再 ReadFile 读取”的两工具任务；失败工具不会让应用崩溃。

## 7. 第三章：Agent Loop

### 目标

让模型在事件流驱动下自主完成多轮“思考—调用—反馈”，并可靠停止。

### 小步

1. 在前两章事件联合类型上加入 `loop_complete`，形成七类 `AgentEvent`：`stream_text`、`tool_use`、`tool_result`、`turn_complete`、`loop_complete`、`usage`、`error`；沿用统一 envelope。
2. 定义显式状态：`READY`、`CALLING_MODEL`、`EXECUTING_TOOLS`、`NEED_CONFIRM`、`COMPLETED`、`CANCELLED`、`FAILED`。
3. 实现单轮：请求模型、收集完整 assistant 内容、判断 tool_use。
4. 实现多轮：执行工具、追加 tool_result、再次请求模型。
5. 实现停止条件：自然结束、最大 50 个 LLM turn、用户取消、连续 3 次未知工具。
6. 用 `asyncio.Event` 传播取消，在模型流、批次之间和下一轮开始前检查。
7. 实现 `partition_tool_calls()`：连续安全调用为并发批，不安全调用独占串行批。
8. 批内并发使用 `gather(return_exceptions=True)`，结果按原调用顺序写回历史。
9. 组装最简 System Prompt：角色、cwd、OS、时间和模式。
10. 增加 `/plan` 与 `/do` 命令和 UI 切换；Plan 只暴露只读工具。

### 自动化测试重点

- `[Read, Read, Edit, Read, Read]` 精确分成三批。
- 其中一个并发工具失败不吞掉同批其他结果。
- 自然结束、达到上限、取消、连续未知工具分别产生正确终态。
- 取消一次循环后还能开始新的用户请求。

### 手动测试

1. 要求查找并总结多个文件，观察并发只读工具。
2. 发起长任务后点击停止，确认应用不退出且可继续聊天。
3. 切到 Plan，确认只读工具仍可见；切回 Do 后确认当前已注册工具恢复。真正的写文件与 Shell 验收到第五章进行。
4. 注册一个测试用错误工具名，观察模型自纠和连续错误保护。

### 常见坑

- 迭代上限按 LLM turn 计数，不按单个 tool call 计数。
- 并发完成顺序不能改变 tool_result 与 tool_use 的对应顺序。
- 只取消 UI 订阅而不取消后台任务会继续花费 Token。

### 退出条件

完成一个至少三轮 LLM 调用、多个工具参与的任务；四种停止路径全部可演示。

## 8. 第四章：System Prompt 设计

### 目标

把静态规则、环境、工具和动态上下文放进正确的 API 字段，并使 Prompt 可测试、可维护。

### 小步

1. 为七个模块分别建立纯文本构建器：角色设定、行为准则、工具指南、代码质量、安全边界、任务模式、输出风格。
2. 实现 `EnvironmentProvider`：cwd、OS、当前时间、Git 分支与简要状态。
3. 实现 `PromptBuilder`，稳定拼接静态模块和环境上下文。
4. 实现 `ContextAssembler`，明确映射到 `system/messages/tools`。
5. 定义带来源与信任级别的 `SystemReminder`，统一 XML 转义。
6. 外部网页、MCP 结果和文件内容标为不可信数据，不能直接构造 reminder。
7. 给 Prompt 生成快照测试，避免无意中改变高缓存命中的前缀。

### 手动测试

1. 打印一次脱敏后的最终请求，核对静态 System Prompt 与环境上下文在 `system`，工具描述在 `tools`，项目指令、自动记忆、System Reminder 与对话历史在 `messages`；尚未实现的来源使用测试夹具占位。
2. 在文件中写伪造 `<system-reminder>`，确认它作为不可信内容进入模型，而非系统提醒。
3. 在 Git 脏工作区询问环境，确认模型知道当前 OS、cwd 和 Git 状态。

### 常见坑

- 动态时间或 Git 状态放在静态 Prompt 前部会破坏缓存前缀。
- XML 标签不能让不可信文本自动升级成系统权限；来源控制比标签名称更重要。
- 工具描述与 System Prompt 重复过多会稀释注意力。

### 退出条件

同一静态配置生成稳定 Prompt；任何外部文本都无法通过普通内容接口变成 reminder。

## 9. 第五章：五层纵深权限防御

### 目标

在工具真正执行前形成不可绕过的集中决策点，并让用户看得懂、能确认。

### 小步

1. 写威胁模型和决策类型：`ALLOW`、`ASK`、`DENY`。
2. 第 1 层实现危险命令硬拦截；规则命中后任何模式都不能放行。
3. 第 2 层实现路径沙箱：规范化、解析符号链接/重解析点、检查项目根边界。
4. 第 3 层实现按工具名、分类和输入摘要匹配的 allow/ask/deny 规则。
5. 第 4 层实现 `trusted`、`accept_edits`、`ask_every_time` 三种模式。
6. 第 5 层实现 `permission_request` 事件、Electron 确认框和异步等待结果。
7. 权限请求展示工具、参数、风险原因和影响路径；日志中脱敏密钥。
8. 所有 mutating 工具统一经过 `PermissionEngine`，工具自身不能绕过。
9. 加入确认超时、用户取消和窗口关闭时的默认拒绝。
10. 本章负责实现最小 `WriteFile` 与 `Bash` 工具并默认接入权限引擎：`WriteFile` 只支持项目内 UTF-8 文本，`Bash` 首版只执行单条非交互命令。第二章只为它们保留接口和 FakeTool 测试，不提前启用真实写操作。

### 关键规则

- 第 1、2 层在所有模式下始终生效。
- “trusted”只是减少确认，不代表系统级安全沙箱。
- 规则默认拒绝未知破坏性工具，默认询问未知写工具，默认允许沙箱内只读工具。

### 手动测试

1. 测试典型根目录删除命令，确认硬拒绝且没有执行痕迹。
2. 用 `..`、绝对路径、大小写变化、符号链接尝试越过项目根。
3. 分别切换三种权限模式，测试读取、创建、覆盖、Shell。
4. 权限弹窗出现时关闭窗口，确认操作被拒绝且后台不悬挂。

### 常见坑

- 只做字符串前缀判断会被 `..`、链接和 Windows 大小写绕过。
- Bash 是否破坏性不能仅靠工具级布尔值判断，仍需命令规则。
- “记住我的选择”如果范围不清，容易生成过宽规则；首版不提供永久记住。

### 退出条件

权限矩阵自动化测试通过，所有写入和 Shell 路径都能追溯到一次明确决策。

## 10. 第六章：MCP 协议

### 目标

同时支持本地 stdio 和远程 Streamable HTTP MCP，失败隔离，并以客户端 ToolSearch 实现跨供应商延迟工具发现。

### 小步

1. 定义 `MCPServerConfig`、连接状态和 `MCPTransport` 接口。
2. 实现 stdio transport，再实现 Streamable HTTP transport。
3. 实现启动时后台连接：initialize、initialized、tools/list。
4. 单个 Server 失败只发警告，不阻止霁雪启动；加入超时和重连上限。
5. 实现 `MCPToolWrapper`，统一命名为 `mcp__服务名__工具名` 并转换结果。
6. MCP 工具默认 `should_defer = true`，注册时不向模型发送完整 Schema。
7. 内置 `ToolSearch` 常驻，支持 `select:完整名` 和关键词搜索。
8. 搜索命中后标记工具为已发现，从下一轮起进入正常 tools 列表。
9. 用环境变量拼接高德 Key，连接高德 Streamable HTTP MCP 做演示。
10. UI 显示 Server 连接状态、延迟发现和调用结果。

### 手动测试

1. 同时配置一个可用和一个不可用 Server，确认应用仍能启动。
2. 首轮请求中检查 MCP 完整 Schema 未被发送，只出现工具名称提醒。
3. 先关键词搜索高德工具，再执行地点或路线类只读查询。
4. 断开网络后观察可理解的错误，恢复后手动重连。

### 常见坑

- URL 中的 Key 不能写入仓库、日志或 UI 错误详情。
- MCP Server 返回的 description 与 content 都是不可信外部文本。
- 工具重名、Server 重连后的重复注册和 Schema 变化需要显式处理。
- Streamable HTTP 生命周期不能套用普通一次性 HTTP 请求。

### 退出条件

高德 MCP 工具经过“名称提醒 → ToolSearch → 完整 Schema → 调用”完整链路成功一次；坏 Server 不影响内置工具。

## 11. 第七章：上下文管理

### 目标

优先保持稳定对话前缀，通过大结果落盘和可恢复摘要控制上下文体积。

### 小步

1. 实现 `ToolResultStore`：单结果超过 50,000 字符时按 tool_use_id 落盘。
2. 使用 Python 独占创建模式 `x`；已存在时复用，不重复写。
3. 实现单消息 200,000 字符聚合预算，优先卸载最大的结果。
4. 历史中保留预览、字符数、哈希和绝对文件路径。
5. 实现上下文预算对象：窗口 − 摘要输出预留 − 安全余量。
6. 实现 `/compact` 手动压缩，再接自动阈值触发。
7. 摘要请求不传 tools，并要求九段结构化 `<summary>`：主要请求、关键概念、文件代码、错误修复、解决过程、用户消息、待办、当前工作、下一步；任何草稿块都丢弃。
8. 压缩后追加最近 5 个文件、已加载项目指令、工具声明和压缩边界消息，严格执行各自预算。Skill 重新注入等 Skill 系统真正加入后再扩展，不属于首版依赖。
9. 摘要失败 3 次后熔断自动压缩；用户仍可手动重试。
10. Prompt Too Long 时按 API turn 分组丢弃最旧组，最多按既定策略重试。

### 手动测试

1. 用假工具生成 49,999、50,001 字符结果，验证阈值两侧行为。
2. 重复整理同一历史，确认磁盘不产生重复文件。
3. 手动压缩后继续追问最近文件内容，确认需要精确内容时模型会重新 ReadFile。
4. 模拟三次摘要失败，确认自动触发停止但普通对话仍可继续。

### 常见坑

- `tool_use_id` 必须清洗或哈希，不能直接作为任意路径。
- 字符数不是精确 Token；首版使用保守估算，并以 API usage 和 Prompt Too Long 兜底。
- 压缩时修改过早的稳定前缀会降低 Prompt Cache 收益。
- 摘要不能被当成文件原文，边界消息必须明确这一点。

### 退出条件

大结果、聚合超限、手动压缩、自动压缩失败熔断四条路径均有测试，压缩后 Agent 可继续工作。

## 12. 第八章：记忆系统

### 目标

把会话恢复、项目知识和用户偏好分层持久化，不把所有历史永久塞进上下文。

### 小步

1. 为消息定义带 `schema_version` 的 JSONL 记录格式。
2. 每条已完成消息追加写入；加载时容忍最后一行因崩溃而不完整。
3. 实现会话创建、列表、恢复和归档；首版不做跨设备同步。
4. 加载项目指令文件，并把内容标记为“本地项目指令来源”。
5. 建立 `.jixue/memory/`：独立 Markdown 记忆文件 + `MEMORY.md` 索引。
6. 定义 YAML frontmatter：id、category、created_at、updated_at、source_session。
7. 索引注入限制为 200 行或 25KB，并在截断时加入警告。
8. 每轮自然结束后启动独立后台提取；不阻塞下一轮对话。
9. 提取器只输出结构化 create/update/delete 建议，客户端验证后才写磁盘。
10. 加入敏感信息过滤、手动 `/remember`、`/forget` 和查看记忆入口。

### 自动记忆类别

- 用户稳定偏好。
- 项目架构与长期约束。
- 经过验证的故障与修复。
- 未完成但跨会话仍重要的任务。

闲聊、临时命令输出、密钥、访问令牌和未经验证的猜测不得自动记忆。

### 手动测试

1. 关闭并重启客户端，恢复上一会话并继续追问。
2. 人为截断 JSONL 最后一行，确认前面记录仍可加载并给警告。
3. 表达一个稳定偏好，等待后台提取，再新建会话验证索引可用。
4. 输入类似 API Key 的文本，确认不会写入记忆文件。
5. 删除一条记忆，确认正文和索引一致更新。

### 常见坑

- 自动提取结果是模型输出，必须验证，不能直接当文件操作执行。
- 多个后台任务同时改索引会丢更新，写入需要进程内锁和原子替换。
- 会话历史与记忆目录包含隐私，默认加入 `.gitignore`。

### 退出条件

会话可恢复；记忆可创建、更新、删除且索引一致；敏感信息过滤测试通过。

## 13. 第九章：最小子 Agent

### 目标

先证明“隔离上下文的受控子任务”可行，不在首版追求 Claude Code 式完整多 Agent 系统。

### 首版设计

- 主 Agent 通过内置 `Task` 工具创建子任务。
- 每个子 Agent 拥有独立 `ConversationManager`、取消信号、轮次预算和事件前缀。
- 只共享不可变的项目环境摘要、Prompt 基线和允许工具列表，不共享主对话可变消息。
- 默认只读，最多并发 2 个，单任务默认 10 turn、5 分钟超时。
- 首版禁止子 Agent 再创建子 Agent，禁止写文件和 Shell。
- 子 Agent 最终只向父 Agent 返回结构化摘要和引用的文件路径，不回灌完整内部历史。
- UI 将子 Agent 事件折叠到独立任务卡片中；父取消会向下传播。

### 小步

1. 定义 `SubagentTask`、预算、状态和结果。
2. 实现只读工具白名单与独立对话。
3. 实现并发上限、超时和级联取消。
4. 把子事件映射到带 `parent_request_id` 的 AgentEvent。
5. 实现 `Task` 工具并向父 Agent 返回结果。
6. UI 展示任务开始、进度、结束和失败。
7. 写清 `v0.2` 扩展点：Git worktree、写权限、专用 Agent 类型和嵌套深度。

### 手动测试

1. 让两个子 Agent 分别阅读不同文件并汇总，确认并发上限和结果隔离。
2. 子 Agent 尝试写文件，确认工具不可见或权限拒绝。
3. 取消父任务，确认两个子任务都结束且无残留协程。
4. 子任务超时后，主 Agent 仍可使用已有结果继续回答。

### 常见坑

- 共享同一个消息列表会造成上下文串线。
- 无预算的递归派发会产生指数级任务和费用。
- 多 Agent 同时写工作区需要真正的隔离；首版用只读约束避免假安全。

### 退出条件

一个主任务可派发两个只读子任务并合并结果；隔离、超时、取消和预算全部可观察。

## 15. Git 路线

- 主分支：`main`，每章从 `feature/chXX-name` 开始。
- 提交尽量小，使用中文说明，例如：`feat(llm): 增加协议无关的流式事件`。
- 推荐提交顺序：领域类型 → 纯逻辑测试 → 适配器 → UI → 文档与手测记录。
- 每章结束合并回 `main`，可选创建 `ch1-done` 等轻量标签；完整回归后创建 `v0.1.0`。
- 不使用提交来掩盖失败测试；开发日志必须记录已知限制。
